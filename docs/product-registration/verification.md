# GardenWorld 상품 등록 검증 기록

2026년 11월 8일 일본 시간에 로컬 분석 웹, GardenWorld 원본 PostgreSQL, 로컬 OpenSearch, 도쿄 리전 S3·Bedrock을 연결했다. 실제 브라우저에서 라벤더와 발렌타인용 꽃을 각각 한 건씩 등록했다.

## 전용 폴더로 이동한 뒤의 재검증 (2026-11-08)

이전한 Python 패키지를 프로젝트 가상환경에 설치하고 웹을 다시 빌드한 다음, 공유 API만 재시작했다. 아래는 새 경로에서 실행한 결과다. 두 상품을 원본에 처음 등록했던 기록은 다음 절부터 구분해 보관한다.

| 환경 | 확인한 결과 |
|---|---|
| 실제 Chrome·공유 호스트 | 기존 `/products/new`에서 일본어 등록 화면과 입력 도우미가 열렸다. 재시작한 `/health`의 분석 계약과 등록 계약은 모두 버전 1이었다. |
| 실제 Laravel → FastAPI → S3·Bedrock·로컬 DB와 검색 | `バレンタイン用花`가 상품명 `花`, 용도 `バレンタイン用`로 추출됐다. 실제 후보 10건 중 기존 `GW-VAL01`이 1위였다. 마스터 3종을 읽고 입수 0은 거부, 6은 통과했다. 도움말과 검사 모두 같은 v4의 `PKG-01`이었다. 기존 라벤더 영수증은 `indexed`였다. 신규 등록 요청은 보내지 않았다. |
| 원본 보존·DB 사전 | 읽기 전용 계정으로 기존 원본 지문과 255 + 등록 이력 2건을 대조했다. 두 상품 코드는 실제 검색 문서와 일치했고 등록 인덱스는 240건이었다. [전체 사전 검증](../database/verification.md)에서 928개 식별자와 등록 FK 5개, 상품을 참조하는 FK 127개를 확인했다. |
| 빌드·모의 시험 | TypeScript·Vite 빌드와 Vitest 20개 통과. Chrome에서 모의 API로 등록·기존 대화 E2E 20개, Laravel 등록 시험 6개(검증문 23개) 통과. Python 선별 회귀 122개 통과. 이 수치에는 예외 상황을 원본 DB에서 재현한 결과가 포함되지 않는다. |
| 격리 PostgreSQL 18.6 | 별도 포트 55439에 공식 GardenWorld 데이터를 복원하고 이전한 DB 설치 코드로 저장 시험을 실행했다. 실제 DB 시험 10개·저장 단위 시험 13개·모의 API 시험 2개가 모두 통과했다(25개, 건너뜀 0). 신규 마스터 3종과 상품의 동시 저장, 실패 시 롤백, 동시 등록, 재전송·색인 복구를 포함한다. 원본 5432에 쓰지 않았으며 격리 서버는 종료했다. 앞의 단위 시험 수치와 일부 겹치므로 합산하지 않는다. |

## 발렌타인용 꽃을 등록하고 새 초안에서 다시 찾기

Chrome에 `バレンタイン用花`를 입력하자 상품명 후보 `花`와 용도 `バレンタイン用`가 표시됐다. 입수를 검증값 1로 지정하고 10개 후보 중 `POCJA-0064 / バラ苗 ワイド`를 선택했다. 오른쪽 도우미에 입력 1과 후보 4가 함께 표시됐고, 입력 화면의 입수는 1이었다. 담당자가 상품명을 원문으로 확정하고 참고 상품의 중량 0.4를 지웠다. 용도와 세금 분류는 그대로 사용했다.

| 확인 지점 | 실제 결과 |
|---|---|
| 항목 도움말과 자유 질문 | 입수의 `?`에서 `PKG-01`, 그램으로 입력해도 되는지 묻는 질문에서 `WGT-01`과 500g → 0.5kg 예시가 나왔다. 최종 검사에는 같은 규칙집 v4가 표시됐다. |
| 오류와 초안 | 입수 0에서 등록 버튼이 비활성화됐다. 원본 DB 조회 결과 상품과 신규 분류는 각각 0건이었다. `修正する`로 입수 칸에 포커스가 돌아왔고 분류 초안이 남아 있었다. 기존 코드 `GW-LAV06`도 `CODE-01` 중복 오류로 차단됐다. |
| 최종 저장 | 코드 `GW-VAL01`, 상품 ID `1000201`. 신규 분류 `GWFLOWER / 贈答用花` 한 건이 상품과 함께 저장됐다. 원본의 기본 단위는 `Each`, 입수는 1, 중량은 SQL NULL, 세금 분류는 `Standard`였다. 원본 상품·등록 이력 조회 결과가 각각 1건이었다. |
| 영수증과 재검색 | 저장 직후 검색 반영 대기, 이어서 반영 완료가 표시됐다. 새로고침해도 같은 ID로 복원됐다. 별도 Chrome 탭의 새 초안에서 동일 문구로 검색한 결과 10개 후보 중 1위였다. 전문 검색·의미 검색 각각 1위였고 검색 문서 ID도 원본 ID와 일치했다. |
| 기존 데이터 보존 | 원본 상품 256 → 257, 등록 전용 인덱스 239 → 240, 분류 14 → 15. 기존 교육용 두 인덱스는 각 200건, 관계 600건, FK 검사 21개 중 고아 행 0건이었다. 최초 기준 파일과 원본 행 지문이 일치했다. |

영수증을 새로고침했을 때 등록 전 재검사를 권하던 안내도 수정했다. 실제 저장된 영수증을 다시 열어 오른쪽 도우미에 `GW-VAL01`과 검색 가능 상태가 표시되고, 다시 검사하라는 문구는 사라진 것을 확인했다.

같은 날 별도 PostgreSQL 18.6과 공식 GardenWorld 데이터를 사용한 저장 시험 10개, 저장 단위 시험 13개, API 장애·복구 모의 시험 2개가 모두 통과했다. 세 종류 마스터의 동시 생성, 저장 도중 롤백, 같은 요청 재전송, 동시 코드 충돌 및 색인 실패 후 재시도를 포함한다. Chrome과 모의 API를 연결한 등록 화면 시험 14개, 규칙·검색 시험 104개도 통과했다. 검색 시험 중 한 건은 실제 로컬 OpenSearch의 임시 인덱스를 사용했다. Laravel 등록 API 연결·CSRF 시험은 6개(검증문 23개)가 통과했다.

## 라벤더 원본 등록 결과

| 원본 DB에서 읽은 항목 | 결과 |
|---|---|
| 상품 코드 / ID | `GW-LAV06` / `1000200` |
| 상품명 / 용도 | `ラベンダー苗・6鉢` / `ベランダ` |
| 기본 단위 / 포장 입수 / 중량 | `鉢` / 6 / SQL NULL |
| 신규 마스터 | 단위 `POT / 鉢` 한 건. 기존 분류와 세금 분류(각 ID 107)를 선택했다. |
| 원본 상품 수 | 255개에서 256개. 등록 영수증·감사·색인 작업으로 입증된 신규 상품 1개. |
| 등록 검색 인덱스 | 선택 가능한 실물 상품 238개에서 239개. 새 상품의 문서 ID가 원본 DB ID와 일치했다. |

실제 브라우저에서 참고 상품 `POCJA-0041`을 선택했다. 참고 상품의 단위가 `Each`여서 확인한 자연어의 `鉢`를 직접 신규 작성했다. 입수에 0을 입력했을 때 `PKG-01`이 오류를 반환했다. 오류 버튼으로 해당 칸에 돌아와 6으로 고쳤고 같은 S3 규칙 버전으로 통과했다. 최종 등록 POST는 한 번이었다. 영수증이 `indexed`로 바뀐 후 실제 검색에서 새 상품이 전문 검색과 의미 검색 양쪽 1위에 올랐다.

최종 화면·규칙 v4를 적용한 뒤 실제 브라우저에서 신규 상품을 검색하고 오른쪽 도우미의 후보 근거와 오류 메시지를 확인했다. 입수 0을 거부한 검사의 버전과 해당 항목 도움말의 버전이 같았다. 원본에 있는 `GW-LAV06`은 중복 오류였고 사용하지 않은 코드의 초안은 검사를 통과했다. 이 두 번째 브라우저 검증에서 등록 요청은 0건이었다.

분석 계정으로 원본의 상품·단위·중량을 다시 읽고 최초 기준 파일의 지문과 대조했다. 기존 교육용 `poc-product`와 `poc-promotion`은 각각 200개이고 관계는 600개였다. 원본·부모 행 보존, 교육 인덱스의 모든 소스 컬럼 일치, FK 21개의 고아 행 0개, 분석 계정의 읽기 전용 검사가 통과했다.

## 실제 AWS와 검색

2026-11-08 Chrome에서 `バレンタイン用花`의 실제 추출 결과가 비고 다음 화면에 후보 0개가 표시되는 증상을 재현했다. 추출 지시·검색 화면을 수정한 뒤 동일한 문구로 실제 Bedrock과 OpenSearch를 다시 호출했다. 상품명은 `花`, 용도는 `バレンタイン用`였고 수량·단위·중량은 빈칸이었다. 추가 입력 없이 다음 단계에서 10개 후보가 표시됐고 첫 두 건은 `バラ苗 ワイド`, `バラ苗 プレミアム`이었다. 이 최초 재현을 마친 뒤 위의 원본 등록·재검색까지 추가 검증했다.

- 프로젝트 계정의 루트 세션으로 도쿄 리전에 `poc-registration` 스택을 설치했다. IAM 사용자 `poc-local-login`으로 이 스택 조회와 앱·규칙 게시 역할 전환을 각각 확인했다. 앱 역할로 S3 규칙을 읽고 Bedrock을 호출했으며 게시 역할로 버전 관리된 규칙 객체를 조건부 갱신했다.
- 최초 원본 등록에 사용한 규칙은 `registration-ja-2026-11-08-v2`이다. 현재 앱 규칙 `registration-ja-2026-11-08-v4`에는 상품명 복사 우선순위와 이름을 모를 때의 입력 예문이 들어 있다. 게시 역할로 다시 읽고 앱 역할로 조회한 v4 SHA-256은 `4f449c24cf80aef12c014cfd87a3d63f00814f6fea54d671fa6004a83f59b291`였다.
- 실제 DeepSeek는 `ベランダ用のラベンダー苗を6鉢入りで登録したい`에서 상품 후보 `ラベンダー苗`, 용도 `ベランダ用`, 수량 6, 단위 표현 `鉢`를 추출했다. 등록 인덱스는 실제 Titan V2의 1,024차원 임베딩과 일본어 전문 검색을 함께 사용했다.

아래는 신규 등록 전 238개 상품에서 미리 지정한 기대 상품군이 상위 10개에 포함되는지 확인한 결과다. 순위는 해당 상품군이 처음 나타난 위치다.

| 입력 | 기대 이름에 포함된 말 | 순위 |
|---|---|---:|
| ラベンダー苗 | ラベンダー | 1 |
| 水やり用のジョウロ | ジョウロ | 1 |
| 有機肥料 | 有機肥料 | 1 |
| 伸びた枝を切りそろえるための道具 | 剪定ばさみ | 3 |
| 日差しを遮ってテラスに日陰を作るもの | 日よけシェード | 4 |

검색 설명도 실제 인덱스로 확인했다. `ラベンダー苗` 검색에서 `ラベンダー コンパクト`(원본 ID 1000040)의 일치어로 OpenSearch가 `ラベンダー`를 돌려줬다. 서버는 현재 PostgreSQL 문자열에도 있는 단어만 후보의 설명으로 전달한다.

## 장애와 동시성 시험 범위

| 환경 | 실행한 검사 |
|---|---|
| 임시 PostgreSQL 18과 공식 GardenWorld 데이터 | 실제 저장 통합 시험 10개 통과. 세 종류 마스터·상품 원자 저장, 코드 중복과 동시 요청, 동일 UUID 재전송, 저장 도중 롤백, 비활성·다른 테넌트 참조, 색인 작업 재시도, 출처 불명 원본 변경 감지를 검증했다. |
| 원본 프로젝트의 Python 회귀 | 기존 분석 기능을 포함하는 `local/python/tests` 최종 전체 실행에서 579개 통과. 선택 실행하는 PostgreSQL 10개와 OpenSearch 1개는 이 명령에서 건너뛰었고, 각각 별도의 통합 환경에서 실행했다. |
| 프런트엔드 및 Laravel | TypeScript·Vite 빌드 통과. Vitest 19개, Laravel 16개(검증문 94개), 실제 브라우저와 모의 상품 API로 상품 등록 13개·기존 대화 6개 통과. 후보 없음과 검색 장애의 구분, 참고 상품 입수 4보다 직접 입력한 6 우선, 초안·마스터 취소, 규칙 변경, 응답 유실 및 동일 요청 재전송을 포함한다. |
| 원본 DB 스키마 | 읽기 전용 카탈로그 대조로 등록 테이블 3개·컬럼 25개·기본/고유 키 6개·FK 5개를 확인했다. 상품을 참조하는 FK는 기존 124개에 등록용 3개를 더한 127개다. 전체 문서 대상, 색인, 개별 문서의 928개 식별자가 일치했다. |

저장 실패·동시성 시험은 격리 DB에서 수행했다. 실제 AWS 연동과 원본 브라우저 검증은 위에 기록한 모델 요청과 라벤더·발렌타인용 꽃 등록 흐름의 결과다.
